# Chunk Metadata & Source Tracking

This document outlines the chunk metadata and source tracking architecture for the `finee.ai` RAG platform.

---

## 1. Why Chunks Must Never Be Stored as Bare Strings

In production RAG systems—especially in high-stakes financial advisory and compliance domains—text chunks must never exist in isolation as unadorned strings.

- **Loss of Provenance**: Storing raw text alone makes it impossible to verify where a statement originated once it is retrieved from a vector database.
- **Inability to Audit**: Financial recommendations must withstand regulatory audits; every claim generated by an LLM requires traceable evidence back to authoritative source records.
- **Context Blindness**: Metadata provides contextual boundaries (e.g., specific document version, page number, section heading) that disambiguate identical or conflicting phrases across multiple documents.

---

## 2. Why Metadata is Necessary for Citations

When generating answers, the LLM must provide verifiable references rather than hallucinations or unattributed assertions:
- **Exact Document & Page Attribution**: Enables users to directly inspect the source page in client records or regulatory filings.
- **Section Grounding**: Clarifies whether a policy applies under "Eligibility Criteria", "Fee Exceptions", or "Standard Terms".
- **Character Boundaries (`char_start`, `char_end`)**: Allows user interfaces to highlight the exact snippet within the original document viewer.

---

## 3. How Metadata Enables Future Filtering

Vector similarity search alone cannot guarantee compliance constraints. Metadata enables pre-retrieval and post-retrieval filtering in the vector database:
- **Version Filtering**: Query only the latest active guidelines (`document_version == "3.2"`).
- **Lifecycle & Approval Filtering**: Restrict retrieval exclusively to documents marked `approval_status == "approved"`, discarding `draft` or `superseded` files.
- **Temporal / Effective Date Filtering**: Prioritize or restrict policies active during the transaction date (`effective_date`).
- **Entity / Client Scoping**: Filter chunks to a specific client record or document ID (`document_id == "doc_001"`).

---

## 4. Why Document Version and Approval Status Matter in Financial RAG

Financial regulations and advisory terms evolve continuously:
1. **Preventing Outdated Guidance**: A chunk stating "Advisory fee is 1.5%" from an old version must not override an updated "Advisory fee is 1.0%" policy in the latest approved release.
2. **Excluding Unapproved Drafts**: Draft or provisional agreements should never influence compliance determinations until officially authorized.
3. **Audit Trail**: Tracking `document_version` and `approval_status` ensures compliance logs can accurately reconstruct what advice was valid at any historical point in time.

---

## 5. End-to-End Provenance Pipeline

```
DOCUMENT
   ↓
EXTRACTION
   ↓
CLEANING
   ↓
CHUNK
   ↓
TEXT + METADATA  (e.g., source, version, page, section, approval_status)
   ↓
EMBEDDING
   ↓
VECTOR DATABASE
   ↓
RETRIEVAL (Vector Search + Metadata Filters)
   ↓
TEXT + METADATA
   ↓
LLM GENERATION
   ↓
ANSWER + SOURCE CITATION
```

## 6. Concrete Example

### User Query:
> *"Did Marcus pay the advisory fee?"*

### Retrieved Chunk:
```json
{
    "text": "Marcus paid the advisory fee on 20 August.",
    "metadata": {
        "source": "Client Payment Record",
        "document_id": "doc_001",
        "document_version": "1.0",
        "chunk_index": 12,
        "page": 2,
        "section": "Payment History",
        "char_start": 1450,
        "char_end": 1494,
        "effective_date": "2026-08-20",
        "approval_status": "approved"
    }
}
```

### Source Citation Output:
```text
Source:
Client Payment Record

Version:
1.0

Page:
2

Section:
Payment History

Chunk:
12

Status:
approved

Effective Date:
2026-08-20
```

### Final Grounded LLM Response:
> *"Yes, Marcus paid the advisory fee on 20 August 2026 [Source: Client Payment Record, Page 2, Payment History (v1.0, Approved)]."*
